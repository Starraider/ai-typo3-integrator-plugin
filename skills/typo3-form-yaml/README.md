# TYPO3 Form YAML

Use this skill for TYPO3 v14 forms built with `typo3/cms-form`, stored as versioned YAML in an extension or site package, secured against spam and attacks, styled for modern frontend frameworks, structured into multi-step dynamic workflows, translated across site languages, and configured with custom branded emails.

## What this skill solves

It keeps EXT:form configuration and `.form.yaml` definitions under source control, selects the appropriate TYPO3 v14 registration mechanism (form sets in v14.2+ vs. legacy fallback), and provides complete recipes for form security, frontend styling, multi-step dynamic forms, multilingual localization, and custom transactional emails. It covers honeypot anti-spam protection, Content Security Policy (CSP) header compliance, and installing, configuring, and adding CAPTCHA fields via `blueways/bw-captcha`. It provides explicit integration patterns for styling forms with Bootstrap Package (`bk2k/bootstrap-package`), Tailwind CSS (with mandatory content scanning), and StyleX (`skom/stylex-connector`). It also details how to create multi-step wizard forms, how to configure dynamic forms using variant conditions that conditionally collect subsequent information (such as asking for attendee quantity and dynamically requesting names and emails per person), how to localize forms using XLF translation files across multilingual sites, and how to customize finisher emails with embedded images and SVGs.

## Use when

- Creating, configuring, or editing versioned `.form.yaml` definitions and form sets in TYPO3 v14.
- Building multi-step wizard forms with step navigation, state persistence, and a review `SummaryPage`.
- Creating dynamic, conditional forms where fields, fieldsets, or entire pages appear or are skipped based on previous user input (e.g., ticket/attendee quantities).
- Translating and localizing forms for multilingual websites using XLF files and the Form translation key chain.
- Protecting forms against spam using built-in honeypots without breaking full-page static caching.
- Configuring Content Security Policy (CSP) headers for form submissions (`form-action`), honeypot styles, and audio CAPTCHA (`media-src blob:`, `connect-src 'self'`).
- Installing and configuring `blueways/bw-captcha` via Site Sets and embedding CAPTCHA elements in form YAML or the TYPO3 Form Editor.
- Styling forms for `bk2k/bootstrap-package` using native Bootstrap 5 markup, multi-column grid rows, and floating labels.
- Styling forms with Tailwind CSS, ensuring utility classes in YAML are scanned and compiled by Tailwind, or using semantic `@apply` components.
- Integrating forms with `skom/stylex-connector` using Fluid partial overrides and `{stylex:class(...)}` ViewHelpers with atomic class manifests.
- Customizing emails generated by `EmailToReceiver` or `EmailToSender` finishers with custom Fluid templates, branded layouts, and table designs.
- Embedding images and SVG graphics in emails with absolute URLs and on-the-fly rasterization for cross-client compatibility (Outlook, Gmail, Apple Mail).

## Expected outputs

- Version-controlled form framework setup under `Configuration/Form/<Set>/config.yaml` and definitions under `Resources/Private/Forms/*.form.yaml`.
- Multi-step definitions with `Page` elements, `SummaryPage`, and conditional variants (`formValues[...]`).
- Localization files under `Resources/Private/Language/Form/locallang.xlf` and language-specific translations (e.g. `de.locallang.xlf`).
- Anti-spam and security configurations: honeypot configuration, CSP directives in `config/sites/<site-identifier>/csp.yaml`, and `blueways/bw-captcha` Site Set activation with `Captcha` renderables.
- Frontend styling configurations matching the project's CSS stack (Bootstrap 5 attributes, Tailwind content scan rules, or StyleX Fluid partials).
- Custom finisher email templates (`.fluid.html` and `.fluid.txt`) with custom layouts, structured form data, and embedded images or converted SVGs.
- A browser, server-side, and email client verification plan covering valid submissions, validation rejections, honeypot blocks, CSP compliance, and email rendering.

## Context requirements

- Exact TYPO3 v14 minor version (v14.2+ form-set auto-discovery vs. earlier minor fallback).
- The owning site package or extension key and path.
- Form architecture requirements (multi-step wizard pages, conditional attendee counts, summary review step).
- Multilingual site configuration (site languages, default language, fallback settings).
- Chosen anti-spam mechanisms (honeypot, `blueways/bw-captcha`, or both) and static caching environment.
- Active CSS pipeline: `bk2k/bootstrap-package` (Bootstrap 5), Tailwind CSS (v3 or v4), or `skom/stylex-connector` (with Vite).
- Email finisher requirements: sender/receiver addresses, custom templates, brand layouts, and graphic asset formats.

## Validation

Read the relevant reference guides before altering configuration or markup:
- [Form Security, Honeypots, CSP, and bw_captcha](references/form-security.md)
- [Multi-Step Forms, Conditions, and Dynamic Fields](references/multistep-conditional-forms.md)
- [Form Translation and Localization across Site Languages](references/form-localization.md)
- [Form Styling with Bootstrap, Tailwind, and StyleX](references/form-styling.md)
- [Custom Email Templates, Layouts, and Image/SVG Embedding](references/email-templates.md)
- [TYPO3 v14 Form Patterns and Registration](references/typo3-v14-form-patterns.md)

After modifying YAML or templates:
1. Rebuild frontend assets (Vite / Tailwind / StyleX) if CSS classes or partials changed.
2. Flush TYPO3 system and page caches (`vendor/bin/typo3 cache:flush`).
3. Verify multi-step navigation: navigate through steps, verify previous/next buttons, and verify conditional fieldsets appear only when corresponding quantities are selected.
4. Verify translations: switch frontend site languages to confirm labels, placeholders, options, and validation messages update.
5. Verify security: submit valid data to confirm finishers execute; submit empty/invalid CAPTCHA values to confirm server-side rejection; and check the browser console for CSP violations.
6. Verify outgoing emails in a local mail catcher (e.g. Mailpit): inspect HTML and plain-text parts, confirm absolute image URLs, and verify SVG rasterization across test clients.
